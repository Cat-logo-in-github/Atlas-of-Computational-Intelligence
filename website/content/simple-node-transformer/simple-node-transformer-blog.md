# Finding the Same Cell Across time: How the Pipeline Learns Temporal Relationships

Finding a cell in one microscopy frame is only half the problem.

The more interesting question is what happens one moment later.

Suppose I have two consecutive frames:

```text
Frame 0                 Frame 1

   A                       D
   B                       E
   C                       F
```

I can detect all six objects.

But now I have to answer:

```text
A → ?
B → ?
C → ?
```

Is A the same cell as D?

Or E?

What about B?

And what happens when a cell divides and one cell becomes two?

This is where I found the second major idea in the pipeline.

The Temporal U-Net is primarily concerned with **finding candidate cells**.

The Simple Node Transformer is concerned with **connecting those cells through time**.

That sounds like a small distinction.

It actually changes the entire problem.

---

## From images to a list of cells

By the time we reach this stage, the pipeline has already processed the microscopy data and extracted candidate cell locations.

A detection might look like:

```text
(t, z, y, x)
```

For example:

```text
0   4   31   82
0   5   74   51
0   7   19   93
```

These coordinates tell us where cells were detected.

But coordinates alone aren't enough.

Imagine two cells that are physically close together.

Their positions might look like:

```text
Cell A → (0, 20, 40, 50)
Cell B → (0, 21, 41, 51)
```

They're close.

But that doesn't necessarily mean they are the same kind of object.

Conversely, a cell may move between frames, so its next location may not be exactly where we expect it.

The transformer therefore needs more information than just location.

It receives two complementary descriptions of every detected cell:

```text
what the cell looks like
+
where the cell is
```

---

## What does "what the cell looks like" mean?

The U-Net has already produced a learned feature map covering the image.

When a cell is detected, the pipeline samples the feature representation at that location.

For each cell, this gives a:

```text
32-dimensional feature
```

It isn't 32 biological measurements.

It's better to think of it as a compact numerical description learned by the neural network.

For example, conceptually:

```text
Cell
 │
 ├── local image structure
 ├── surrounding context
 ├── visual patterns
 └── other learned signals
```

The network has converted all of that into:

```text
[0.14, -0.31, 0.82, ...]
```

with 32 values.

We don't manually assign meanings to individual values.

The model learned how to use them during training.

So this part of the representation answers:

> **"What does this detected cell look like in the image?"**

---

## But appearance isn't enough

Now consider a different situation.

Suppose two cells look almost identical.

That is completely plausible biologically.

A neural network looking only at their appearance might have difficulty distinguishing them.

But their positions could be very different.

For tracking, position is extremely valuable.

So the pipeline adds a second representation.

This time, it starts from:

```text
(t, z, y, x)
```

and converts those four coordinates into:

```text
32 positional values
```

This is called a **sinusoidal positional encoding**.

The name sounds more intimidating than the idea actually is.

---

## Turning a location into a richer signal

Suppose a cell is located at:

```text
(t, z, y, x)
```

The pipeline first normalizes those coordinates relative to the dimensions of the input.

Then each coordinate is represented using several frequencies.

For each coordinate, it uses:

```text
frequency 1
frequency 2
frequency 4
frequency 8
```

And for every frequency, it calculates both:

```text
sin(angle)
cos(angle)
```

So:

```text
4 frequencies
×
2 functions
=
8 values
```

There are four coordinates:

```text
t
z
y
x
```

Therefore:

```text
4 coordinates
×
8 values
=
32 values
```

The structure is roughly:

```text
t → 8 values
z → 8 values
y → 8 values
x → 8 values

        ↓

32-D positional representation
```

The important thing to understand is that these 32 numbers are **not 32 new physical measurements**.

![](../temporal-unet/assets/video2_frame5_32d_positional_to_64d_node_feature%20(1).mp4)

There are still only four original coordinates.

The encoding is simply a richer mathematical representation of those four coordinates.

---

## Why use sine and cosine?

A useful way to think about this is to imagine describing a location using several waves.

A slow wave changes gradually:

```text
~        ~        ~        ~
```

A faster wave changes more quickly:

```text
~~~~  ~~~~  ~~~~  ~~~~
```

And an even faster one changes more rapidly:

```text
~~~~~~~~~~~~
```

The pipeline uses several such frequencies.

For each one, it records both sine and cosine.

That gives the model multiple views of where the cell is.

The purpose isn't to make the coordinate more physically accurate.

The purpose is to give the neural network a representation from which it can learn positional relationships more easily.

In other words:

```text
raw coordinate
     ↓
mathematical encoding
     ↓
richer positional feature
```

---

## Position is not cell size

This distinction is particularly important.

The positional encoding tells the transformer:

> "This cell is here."

It does **not** tell it:

> "This cell is 12 micrometers wide."

It does not directly encode:

```text
cell radius
cell volume
cell diameter
cell shape
```

Those kinds of visual characteristics are represented through the learned U-Net feature.

So the two components have different jobs:

```text
U-Net feature
    ↓
What does this cell look like?

Positional encoding
    ↓
Where is this cell?
```

The pipeline deliberately combines both.

---

## Building the 64-dimensional cell representation

Now the two halves come together.

For every detected cell:

```text
32-D U-Net feature
        +
32-D positional feature
        │
        ▼
64-D node representation
```

You can visualize it as:

```text
┌──────────────────────────────────────────┐
│          32-D U-Net feature              │
│      learned image representation        │
├──────────────────────────────────────────┤
│        32-D positional feature           │
│     deterministic location encoding      │
└──────────────────────────────────────────┘
```

This 64-dimensional vector is what the downstream transformer works with.

I found this one of the clearest examples of how machine-learning systems combine different kinds of information.

One part is learned from the microscope image.

The other part is constructed from known coordinates.

Neither is sufficient on its own.

Together, they provide a much more useful description of a cell.

![](./assets/asset_7A_node_representation.mp4)

---

## Now the problem becomes a matching problem

Imagine two frames again:

```text
Frame t                 Frame t+1

 A                        D
 B                        E
 C                        F
```

Each object now has a 64-dimensional representation.

So the transformer can compare:

```text
A with D
A with E
A with F

B with D
B with E
B with F

C with D
C with E
C with F
```

For three cells in each frame, that creates a matrix:

```text
             Target

             D       E       F

Source A     ?       ?       ?

       B     ?       ?       ?

       C     ?       ?       ?
```

The transformer fills this with compatibility scores.

For example:

```text
             D       E       F

A           2.1    -1.2     0.4

B          -0.8     3.7     0.1

C           0.2    -0.4     4.2
```

The larger the score, the stronger the model's preference for that relationship.

But these are still **not graph edges**.

They are model outputs that need to be interpreted and filtered.

---

## What is the transformer actually comparing?

This is where the architecture becomes easier to understand if we avoid thinking of it as magic.

For a possible connection:

```text
Cell A at time t
        │
        │
        ▼
   Transformer
        ▲
        │
        │
Cell D at time t+1
```

the model has access to representations containing:

```text
A:
appearance + position

D:
appearance + position
```

So it can learn relationships involving both.

For example, conceptually:

```text
similar appearance
+
reasonable spatial movement
+
compatible temporal position
        ↓
stronger relationship
```

Whereas:

```text
very different appearance
+
large unexpected displacement
        ↓
weaker relationship
```

The actual neural network learns these relationships rather than using a hand-written rule like:

```text
if distance < X then connect
```

That distinction matters.

The pipeline is not simply drawing lines between the closest cells.

![](./assets/asset_7B_real_cross_attention.mp4)

It is using learned representations to score possible temporal relationships.

---

## Why not just connect the nearest cell?

This is probably the most natural question.

If a cell moves only a little between frames, why not simply find the nearest cell?

Because biological images aren't always that cooperative.

Cells can:

* move,
* change appearance,
* come close to one another,
* divide,
* disappear,
* or appear differently because of imaging conditions.

A nearest-neighbor rule has no real understanding of what it is matching.

Imagine:

```text
Frame t:

        A
        B
```

and in the next frame:

```text
Frame t+1:

        D
       E
```

If A and B are close together, simple distance might not be enough to decide which is which.

The transformer has more information available.

It sees learned image features as well as position.

That gives it a chance to learn relationships that are more meaningful than pure geometric proximity.

![](./assets/asset_7C_real_edge_logits%20(2).mp4)

---

## From scores to probabilities

The raw transformer outputs are called **edge logits**.

These are transformed into probabilities.

The supplied configuration uses:

```text
edge_activation = "softmax"
```

Softmax makes the candidate targets compete with one another.

For a source cell A:

```text
A → D    score = 2.1
A → E    score = -1.2
A → F    score = 0.4
```

the softmax converts those values into a distribution where the candidates are compared relative to each other.

Conceptually:

```text
A
│
├── D → high probability
├── E → low probability
└── F → medium probability
```

![](./assets/asset_7D_real_edge_probability_softmax.mp4)

This gives the model's output a useful interpretation:

> **Among these possible targets, which one is this source cell most compatible with?**

That is different from a sigmoid.

With sigmoid, each source-target pair can be considered independently.

With softmax, the candidates compete.

The current inference configuration uses softmax.

---

## The probability isn't the final decision

This is another subtle but important part of the design.

Suppose the transformer produces:

```text
A → D = 0.82
A → E = 0.64
A → F = 0.12
```

It would be tempting to simply say:

```text
connect A to D
connect A to E
ignore F
```

But that could create biologically strange graphs.

A cell normally shouldn't have an arbitrary number of children.

So the pipeline applies additional constraints after calculating the probabilities.

This is where the neural prediction meets biological structure.

---

## Allowing cell division

The graph rules include:

```text
max_parents_per_node = 1
max_children_per_node = 2
```

This reflects an important biological assumption.

A cell normally has at most one parent.

But a cell can divide into two daughters.

So the graph can represent:

```text
Normal continuation

       A
       │
       ▼
       B
```

and:

```text
Division

       A
      / \
     ▼   ▼
     B   C
```

This is much more appropriate for cell tracking than simply forcing every cell to have exactly one successor.

The graph structure is therefore informed by biology.

The model predicts possible relationships, but the pipeline also knows that certain kinds of relationships make more sense than others.

---

## The transformer doesn't produce complete tracks

This is another distinction worth keeping clear.

The transformer doesn't output:

```text
Track 1 = A → B → D → G
Track 2 = C → F → H
```

Instead, it produces **pairwise temporal relationships**.

For example:

```text
A → B
B → D
C → F
```

Those relationships can then be assembled into a larger tracking graph.

So the transformation is:

```text
cell representations
       ↓
pairwise comparisons
       ↓
edge scores
       ↓
edge probabilities
       ↓
accepted temporal relationships
       ↓
tracking graph
```

The final track structure emerges from the graph.

This separation makes the system much easier to reason about.

---

## Every edge also has a distance

The pipeline stores another useful property for accepted edges:

```text
edge_dist
```

So an edge conceptually contains:

```text
source
target
edge probability
spatial distance
```

These two numbers mean different things.

The probability says:

> "How strongly does the model support this relationship?"

The distance says:

> "How far apart are these two detections?"

For example:

```text
A → B

probability = 0.91
distance    = 4.7
```

The distance isn't replacing the learned prediction.

It's additional information about the resulting relationship.

This becomes particularly useful when inspecting or evaluating the final tracking graph.

## A cell's journey through this stage

At this point, I find it useful to follow one hypothetical cell.

We start with the microscope:

```text
3D image
```

The U-Net processes it.

A detection appears:

```text
Cell A
(t, z, y, x)
```

The pipeline samples the U-Net feature:

```text
32-D learned feature
```

It encodes the position:

```text
32-D positional feature
```

Then:

```text
32 + 32
   ↓
64-D node
```

Now the node can be compared with cells in the next frame.

Suppose there are three possible targets:

```text
D
E
F
```

The transformer produces:

```text
A → D = strong
A → E = weak
A → F = very weak
```

![](./assets/video2_frame7_64d_nodes_candidate_pairs.mp4)

After probability conversion and graph filtering, perhaps:

```text
A ─────────→ D
```

survives.

That one relationship eventually becomes one edge in the tracking graph.

Repeat that process for all detected cells and all consecutive frames, and the graph starts to take shape.

## Why this architecture makes sense for biology

The more I looked at the pipeline, the more natural the separation became.

A microscopy image contains enormous amounts of information.

The U-Net reduces that complexity into useful local representations and candidate cell locations.

The transformer then operates on a much smaller set of objects.

Instead of comparing every voxel with every voxel, it works with:

```text
cell → cell
```

relationships.

That is a much more manageable problem.

The conceptual progression is:

```text
Microscopy image
       ↓
learned visual representation
       ↓
candidate cells
       ↓
cell representations
       ↓
candidate relationships
       ↓
temporal graph
```

Each step reduces the problem to a more structured form.

---

## The most useful mental model

If I had to explain the Simple Node Transformer to someone who knows biology but not machine learning, I would describe it this way:

Imagine looking at two microscope frames and putting a small card next to every detected cell.

Each card contains two things:

```text
"What does this cell look like?"
+
"Where is this cell?"
```

The transformer takes the cards from two consecutive frames and asks:

> "Which cards appear to describe the same biological object continuing through time?"

It doesn't immediately draw the final family tree.

It scores possible relationships.

The graph-building stage then decides which of those relationships should actually be kept.

So the pipeline moves from:

```text
CELLS
```

to:

```text
POSSIBLE RELATIONSHIPS
```

before eventually becoming:

```text
TRACKING GRAPH
```

That distinction is, for me, the key to understanding this part of the system.

**Once we have these predicted relationships, how does the pipeline turn them into an actual tracking graph?**
